# Laporan Pengujian Ketahanan dan Fault Injection (`superapp-gateway`)

Dokumen ini memuat hasil pengujian *fault injection* untuk mengukur ketahanan (*resilience*), isolasi kegagalan (*blast radius*), waktu deteksi, serta waktu pemulihan (*recovery time*) pada arsitektur **SuperApp Gateway** (`project: superapp`, jaringan Docker `superapp_default`, gateway NGINX di `http://127.0.0.1:8080`).

---

## 1. Metodologi & Konfigurasi Probe

### 1.1. Aturan Eksekusi & Isolasi Gangguan
- **Satu gangguan dalam satu waktu (*single fault at a time*)**: Setiap skenario dijalankan secara berurutan melalui orkestrator [`gateway/tests/fault/run-fault.ps1`](../gateway/tests/fault/run-fault.ps1).
- **Pemulihan otomatis (`try/finally`)**: Setiap skenario dibungkus blok `try/finally` yang selalu memulihkan kondisi layanan (`docker compose start`, `docker unpause`, `docker network connect --alias judul-api`, pengembalian alokasi CPU ke jumlah vCPU host), menunggu seluruh 9 container kembali `healthy` (batas waktu maksimal 180 detik), dan memberi jeda *cooldown* 15 detik sebelum skenario berikutnya.
- **Tanpa panggilan LLM**: Seluruh probe dan skenario aktif menghindari pemanggilan endpoint LLM berbayar (OpenAI maupun Groq).

### 1.2. Probe Latar Belakang (`P1`–`P6`)
Selama tiap skenario aktif, 6 pekerja probe latar belakang ([`gateway/tests/fault/probe-worker.ps1`](../gateway/tests/fault/probe-worker.ps1)) berjalan paralel dengan interval **500 ms** (~2 req/detik per probe) menggunakan `curl.exe -m 10` dan mencatat `timestamp_ms`, nama probe, kode HTTP, waktu respons (`time_total_s`), status keberhasilan (`is_ok`), serta ringkasan isi respons ke `gateway/tests/fault/out/probes-<skenario>.csv`:

| Probe | Endpoint via Gateway (`127.0.0.1:8080`) | Autentikasi | Kriteria Sukses (`is_ok = 1`) | Layanan yang Diuji |
| :--- | :--- | :--- | :--- | :--- |
| **P1** | `GET /healthz` | Publik (`auth_request off`) | HTTP `200` | NGINX Gateway sendiri |
| **P2** | `GET /api/micro-cred/tracks` | `Bearer <token>` | HTTP `200` | NGINX + `auth-verifier` + `microcred-api` + `db` (PostgreSQL) |
| **P3** | `GET /api/judul-recommender/` | `Bearer <token>` | HTTP `200` | NGINX + `auth-verifier` + `judul-api` |
| **P4** | `POST /api/matkul-recommender/panduan/extract-upload` (file kecil non-PDF) | `Bearer <token>` | HTTP `400` (validasi aplikasi, bukan `5xx`) | NGINX + `auth-verifier` + `matkul` |
| **P5** | `GET /api/micro-cred/health` | Publik (`auth_request off`) | HTTP `200` **dan** JSON `status == "ok"` | NGINX + `microcred-api` + konektivitas `db` & `redis` |
| **P6** | `POST /api/micro-cred/auth/login` (email tidak terdaftar) | Publik (`auth_request off`) | HTTP `401` (ditolak aplikasi, bukan `5xx`) | NGINX + `microcred-api` + `db` (jalur tulis/baca auth publik) |

### 1.3. Definisi Metrik Waktu
- **Waktu hingga galat (*time-to-error*)**: Waktu respons satu request terpisah (`curl.exe -m 150`) yang dikirim segera setelah gangguan disuntikkan.
- **Waktu deteksi probe**: Selisih waktu sejak gangguan disuntikkan hingga sampel probe target pertama yang mencatat `is_ok = 0`.
- **Waktu pemulihan (sukses pertama)**: Selisih waktu sejak perintah pemulihan dijalankan hingga sampel probe target pertama yang kembali mencatat `is_ok = 1`.
- **Waktu pemulihan (10 sukses beruntun)**: Selisih waktu sejak perintah pemulihan dijalankan hingga probe target mencapai **10 sampel sukses berturut-turut** (~5 detik stabil pada interval 500 ms).

## 3. Analisis Mendalam Temuan Utama

### 3.1. Isolasi Kegagalan (*Blast Radius*) & Perilaku Timeout NGINX (`F1`, `F3`, `F4`, `F5`)
1. **Isolasi antar-layanan berfungsi penuh**: Matinya `judul-api` (`F1a`), `matkul` (`F1c`), atau membekunya `judul-api` selama 90 detik (`F4`) sama sekali tidak menimbulkan kegagalan (0% *error rate*) pada layanan lain yang berbagi gateway NGINX.
2. **Kemandirian Verifikasi JWT (`F1b` vs `F3a`/`F3b`)**:
   - Ketika `microcred-api` mati (`F1b`), mahasiswa yang sudah memiliki token JWT tetap dapat mengakses layanan Judul (`P3`) dan Matkul (`P4`) tanpa gangguan karena verifikasi tanda tangan dan *role* dilakukan secara mandiri oleh `auth-verifier`.
   - Sebaliknya, ketika `auth-verifier` mati (`F3a`) atau membeku (`F3b`), seluruh rute terproteksi (`P2, P3, P4`) langsung menolak akses dengan `HTTP 503` (`{"detail":"Layanan autentikasi tidak tersedia"}`) dalam waktu **2,0 detik** (`F3a`, `proxy_connect_timeout 2s`) hingga **3,0 detik** (`F3b`, `proxy_read_timeout 3s`), sementara rute publik (`P1, P5, P6`) tetap beroperasi normal.
3. **Perbedaan *Container Stop* (`F1a`) vs *Network Disconnect* (`F5`) vs *Process Freeze* (`F4`)**:
   - Pada `F1a` (`stop judul-api`), request pertama mengalami timeout koneksi `5,006s` (`504`), lalu setelah entri ARP/bridge diperbarui, request berikutnya langsung ditolak dalam `0,006s` dengan `HTTP 502 Bad Gateway`.
   - Pada `F5` (`network disconnect`), karena paket TCP SYN jatuh ke *blackhole* tanpa balasan RST/ICMP, setiap request secara konsisten tertahan selama **5,009 detik** (`proxy_connect_timeout 5s`) dan berakhir dengan `HTTP 504 Gateway Timeout`.
   - Pada `F4` (`pause judul-api`), jabat tangan TCP berhasil diselesaikan oleh kernel sebelum/saat proses dibekukan namun aplikasi tidak mengirim byte respons, sehingga NGINX menunggu penuh selama **60,001 detik** (`proxy_read_timeout 60s`) sebelum mengembalikan `HTTP 504 Gateway Timeout`.

### 3.2. Resolusi DNS Upstream NGINX & Alias Jaringan Docker (`F2` & `F5`)
- Pada konfigurasi [`gateway/nginx/nginx.conf`](../gateway/nginx/nginx.conf) saat ini, setiap upstream ditulis secara statis di blok `upstream ... { server <nama-service>:<port>; }` tanpa direktif `resolver`. Akibatnya, NGINX hanya me-resolve nama DNS menjadi alamat IP satu kali saat *startup*.
- Pada `F2` (`docker compose up -d --force-recreate judul-api`), teramati bahwa `StartedAt` container `superapp-nginx-1` **tidak berubah** (Docker Compose tidak me-restart `nginx` ketika perintah `up -d --force-recreate` hanya menargetkan `judul-api`). Sistem tetap pulih otomatis semata-mata karena Docker IPAM memberikan kembali alamat IP `172.20.0.6` yang baru saja dilepas kepada container `judul-api` yang baru.
- Pada `F5`, ditemukan bahwa menjalankan `docker network disconnect superapp_default superapp-judul-api-1` diikuti `docker network connect superapp_default superapp-judul-api-1` **tanpa flag `--alias judul-api`** hanya mendaftarkan nama container (`superapp-judul-api-1`) ke DNS internal Docker (`127.0.0.11`) dan menghilangkan alias service `judul-api`. Jika setelah itu `nginx` di-restart, `nginx` akan gagal *startup* (`[emerg] host not found in upstream "judul-api:8001"`). Penggunaan `--alias judul-api` saat `network connect` mencegah masalah ini.

### 3.3. Ketahanan Datastore Micro-cred (`F6a` & `F6b`)
- **Kegagalan Redis (`F6a`)**: Menghentikan `redis` hanya membuat `/api/micro-cred/health` (`P5`) berubah menjadi `status: "degraded"` (dengan waktu respons ~8 detik karena percobaan koneksi Redis), sedangkan endpoint `/tracks` (`P2`) dan `/auth/login` (`P6`) tetap melayani dalam ~10 ms tanpa galat.
- **Kegagalan PostgreSQL (`F6b`)**: Menghentikan `db` menyebabkan `/tracks` (`P2`) dan `/auth/login` (`P6`) gagal dengan `HTTP 500 Internal Server Error`. Namun begitu `db` dinyalakan kembali, `microcred-api` **pulih otomatis dalam 2,87 detik** tanpa perlu me-restart container `microcred-api` berkat konfigurasi `pool_pre_ping=True` pada SQLAlchemy async engine. Integritas data terverifikasi utuh (**101 baris** pada tabel `users` sebelum dan sesudah `db` dihentikan).

## 4. Usulan Perbaikan (Rekomendasi Arsitektur & Konfigurasi)

> **Catatan**: Sesuai aturan pengujian, daftar perbaikan di bawah ini hanya berupa usulan berdasarkan temuan empiris dan **tidak diimplementasikan** pada kode saat ini.

1. **Gunakan `resolver 127.0.0.11 valid=10s;` dengan variabel pada `proxy_pass` di `nginx.conf` (Temuan `F2`, `F5`, `F8`)**:
   - Menambahkan `resolver 127.0.0.11 valid=10s ipv6=off;` di level `http` atau `server` pada [`gateway/nginx/nginx.conf`](../gateway/nginx/nginx.conf) serta menyimpan nama host upstream dalam variabel (misalnya `set $judul_upstream http://judul-api:8001; proxy_pass $judul_upstream;`) akan membuat NGINX me-resolve ulang IP container secara dinamis setiap 10 detik tanpa perlu restart `nginx` saat IP container berubah, sekaligus mencegah NGINX gagal *startup* bila salah satu container upstream sedang belum siap resolusi DNS-nya.
2. **Bedakan `proxy_read_timeout` antara rute cepat dan rute LLM/ekstraksi berat (Temuan `F4`)**:
   - Saat ini seluruh lokasi di `nginx.conf` (kecuali `/_auth`) memakai `proxy_read_timeout 60s`. Untuk rute katalog, profil, dan metadata cepat (seperti `GET /api/micro-cred/tracks`, `GET /api/micro-cred/auth/me`, `GET /api/judul-recommender/`), menurunkan `proxy_read_timeout` ke **10–15 detik** akan mempercepat *fail-fast* ketika backend membeku, sementara `proxy_read_timeout 60s` (atau `90s`) dipertahankan khusus untuk endpoint skoring LLM dan upload PDF.
3. **Hubungkan `SubmissionService._create_async_jobs` dengan antrean Redis RQ atau selaraskan arsitektur worker (Temuan `F11`)**:
   - Pada [`services/microcred/src/domain/services/submission.py`](../services/microcred/src/domain/services/submission.py), fungsi `_create_async_jobs` perlu memanggil `queue.enqueue(process_gpt_job, ...)` ke Redis saat `settings.auto_process_jobs` bernilai `False`, sehingga `microcred-worker` benar-benar mengeksekusi pipeline di luar proses `microcred-api`. Jika pemrosesan via `BackgroundTasks` ingin dipertahankan sebagai satu-satunya mekanisme, dokumentasikan bahwa `AUTO_PROCESS_JOBS=true` wajib aktif dan container `microcred-worker` dapat dinonaktifkan untuk menghemat memori.
4. **Ekspos status `degraded: true` saat fallback LLM atau RAG aktif (Temuan `F10`)**:
   - Pada pipeline skoring esai dan RAG di Micro-cred, ketika terjadi kegagalan panggilan API eksternal (seperti habisnya kuota/kredit OpenAI yang memicu `essay_scoring_fallback_used` atau `rag_fallback_activated`), setel flag `degraded = True` pada payload hasil assessment dan simpan alasan degradasi agar pengguna maupun frontend mengetahui bahwa skor yang tampil merupakan hasil estimasi fallback, bukan evaluasi GPT penuh.
5. **Kembalikan HTTP `503 Service Unavailable` pada `/api/micro-cred/health` dan tangani `DBAPIError`/`OperationalError` menjadi `503` (Temuan `F6a` & `F6b`)**:
   - Pada [`services/microcred/src/api/routes/health.py`](../services/microcred/src/api/routes/health.py), kembalikan kode status HTTP `503` ketika PostgreSQL berstatus `error` agar orkestrator container (Docker healthcheck / load balancer) mengenali bahwa instans sedang tidak sehat. Selain itu, tambahkan *exception handler* global untuk `SQLAlchemyError` / `OSError` koneksi DB agar mengembalikan `503` JSON yang rapi, bukan `500 Internal Server Error`.

## 5. Keterbatasan Pengujian

1. **Lingkungan Satu Mesin (*Single-Host Docker Desktop*)**: Seluruh 9 container stack, proses probe PowerShell, dan container beban `k6` berjalan pada satu mesin host Windows yang sama, sehingga metrik latensi dan waktu pemulihan dipengaruhi oleh penjadwalan CPU host serta lapisan virtualisasi jaringan WSL2/Docker Desktop.
2. **Satu Gangguan dalam Satu Waktu (*Single Fault Injection*)**: Pengujian dilakukan secara sekuensial dengan satu gangguan per skenario dan jeda pemulihan penuh di antaranya; skenario kegagalan majemuk bersamaan (*correlated/cascading multi-faults*, misalnya `db` lambat bersamaan dengan lonjakan trafik dan habisnya koneksi Redis) belum diuji.
3. **Resolusi Waktu Probe Latar Belakang (Interval 500 ms / ~2 req/detik)**: Probe latar belakang berjalan setiap 500 ms per endpoint (total ~12 req/detik untuk 6 probe) dengan batas waktu `curl -m 10`, sehingga waktu deteksi dan waktu pemulihan memiliki resolusi granularitas ±0,5 detik dan gangguan mikro di bawah 400 ms dapat terlewat di antara dua siklus probe.
4. **Perilaku Alokasi IP Docker IPAM**: Pada skenario `F2` (`--force-recreate`), Docker IPAM pada jaringan bridge `superapp_default` tanpa container baru lain yang menyela selalu memberikan kembali alamat IP yang sama (`172.20.0.6`), sehingga masalah *stale IP caching* pada NGINX baru akan memicu kegagalan nyata apabila ada container lain yang mengambil IP tersebut di sela waktu *recreate*.
